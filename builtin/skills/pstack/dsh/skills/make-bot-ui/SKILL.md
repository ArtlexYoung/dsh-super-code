# Build a UI that delegates to DSH

Keep the original end-to-end workflow: a user clicks a page, a backend submits the chosen task, DSH handles it, and the page shows progress and results. Use this plugin's MCP connection instead of a host-specific webhook routine.

1. In DSH Super Code settings, enable Connection deliberately and allow only the intended workspace. Use the displayed MCP URL and credential. Keep the credential in the backend's environment or a user-managed secret file; never in browser JavaScript, chat, logs or the Skill. Do not turn on caller approval unless the user explicitly requests it.
2. Build the backend with an MCP client supporting Streamable HTTP (for example the project's existing MCP SDK). Connect to the configured URL using bearer authentication. Run `dsh_status` to verify identity, directory authorization and capacity. Do not launch a second DSH or read its profile to bypass a connection error.
3. Discover the current tool schema through MCP. Before submission, call `dsh_sessions` for the chosen cwd. Let the user select an available existing taskId or explicitly choose a new conversation when `allowNewConversations` is true. Respect linked-connection and active-task counts. A taskId identifies the reusable conversation, not an individual turn: keep requestId records and prior results separate from its current turn. Do not silently reuse the latest conversation.
4. Validate the UI's small, named action schema in the backend; browser fields and returned content are data, not permission to run arbitrary instructions. Map each allowed action to its fixed task prompt. Use the bundled [stable submission helper](references/submissions.md) for a stable requestId, canonical execution payload, same-ID admission and restart recovery. Include validated arguments, cwd, exact prompt, explicit conversation and confirmed optional model choice in that payload. Follow its conflict and persistence-error contracts; use `receipts()` to restore this backend's owned task IDs. Keep the MCP credential out of the payload/store. Do not replace the helper with a requestId-only cache or silently generate a new ID on retry. Use exact optional provider/model/effort IDs from `dsh_models`; omitted fields inherit the host.
5. Track the returned taskId using `dsh_wait` and its returned cursor. Preserve the returned status strings, including `starting`, `running`, `waiting_confirmation`, `cancelling`, `finished`, `failed`, `cancelled`, `interrupted` and `unavailable`, and display unknown statuses explicitly. Only `finished`, `failed` and `cancelled` are settled. Keep observing `interrupted` and `unavailable`, which can still own active work; retain explicit cancellation and never resubmit automatically. Use `dsh_read` to retrieve paged public results when needed. A finished turn is not proof of correctness. Display `waiting_confirmation` even when caller approval is disabled and `callerApproval.pending` is empty; direct the user to DSH via the returned nextAction. The backend must not auto-approve. Cancel only the task this UI owns on an explicit cancel action, and observe its settled result rather than treating the cancellation request as completion.
6. Bind the page backend to loopback by default. If remote access is requested, inspect the existing authenticated proxy or tailnet state and reuse its node; report the actual hostname/address and verified URL. Configure the minimal authorized bind/proxy route, then probe it from the intended client path. Installing or authenticating new network software needs its own authorization and the real provider's login flow. Keep the MCP credential server-side. Never guess an endpoint or claim that a localhost probe proves remote reachability.
7. Verify the complete path with a harmless task in a task-owned workspace: user selection, submission, identical and concurrent same-ID retries, same-ID changed-content rejection, backend restart, progress, approval/error display and final public result. For retained HTTP evidence, use the [capture helper](../../scripts/capture.mjs) from this workspace: `node "<PSTACK_ROOT>/scripts/capture.mjs" curl -sS -i <URL>` (add request arguments as needed). It saves both response and exit status in a new project-local run directory; read and cite the returned files. Save screenshots under this project's evidence directory. Keep evidence for review and use recoverable cleanup when requested. Confirm that no credential enters browser bundles, responses, screenshots or logs. Test denied directories and disabled new conversations. Reuse one MCP session. On cleanup or replacement of a failed transport, attempt its terminateSession (HTTP DELETE) before closing the client and report any cleanup failure; then stop only this run's backend and keep its evidence. A local client close alone does not release the server connection.

Report the real UI URL, selected DSH workspace/conversation, what was verified and any missing dependency. If MCP is unavailable, pause the connection-dependent phase with the exact setup needed; do not invent an equivalent host API or claim the bot was awakened.
