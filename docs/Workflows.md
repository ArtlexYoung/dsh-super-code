# 工作流

在会话顶部打开「工作流」，可浏览随插件提供的四套 Skill。默认关闭的包仍显示在目录中；需要使用时，在「设置 → Super Code 模式 → 预置 Skill」启用对应包，并选用允许 Skill 的会话预设。

「推进工作」把当前目标、阶段流程和会话执行放在一起。阶段卡显示目标产物和状态；选择阶段后，可以准备真实 Skill 指令、记录成果、关联文件、标记阻塞或确认验收。进展反馈对应实际工作记录，每个阶段都可以直接查看，并按任务需要继续。

路线依据随包提供的作者文档组织。展开流程下方的作者方法可查看条件和原文；这是 Super Code 对这些工作方法的可视化，并非作者提供的任务执行系统。

| 工作流 | 使用方式 |
| --- | --- |
| Matt · 单会话小任务 | 在项目中用 `grill-with-docs` 澄清并记录，需求已清楚时直接 `implement`，最后 `retro`。实现阶段包含约定接缝上的 TDD 和 Standards + Spec 双轴审查。 |
| Matt · 多任务实现 | `grill-with-docs` → `to-spec` → `to-tickets` → 逐票 `implement` → `retro`。按依赖领取可执行任务；也可按需改用 `implement-spec` 编排整张任务图。 |
| Matt · 故障修复 | `diagnosing-bugs` 先建立稳定失败的反馈，再定位与修复；随后审查改动、复盘工作环境。 |
| Matt · 复杂探索 | `wayfinder` 先建立决策地图、解决当前未阻塞的决策，等路径清楚再交给 `to-spec`。探索地图默认产生决策，不直接实施功能。 |
| PStack · Feature | 由 `poteto-mode` 驱动，依次理解现状、确定数据与接口、安排可验证单元、实现复核、在真实入口验证。 |
| PStack · Refactoring | 由 `poteto-mode` 驱动，先固定行为基线，再确定结构、删减迁移、证明行为一致。 |
| OpenSpec | 探索、提案、实施、验证与归档。 |
| oil-ui | 明确用户任务、建立结构、实现界面，再检查真实画面与操作。 |

Matt 的原型是有疑问时才进入的支线；项目首次使用需要按 `setup-matt-pocock-skills` 配置任务后端和文档位置。PStack 的模型设置按需配置，长任务从开始就用 `show-me-your-work` 保留决策轨迹；`sharpen` 深化提示词，本身不修改代码。这些入口放在流程的「按需工具」中。委派、远程写入、发布等仍遵守当前项目和会话授权。

「Skill 目录」可按包、关键词、收藏或最近使用查找全部 Skill，每页最多展示 24 项。详情保留原文说明、内容结构、版本和来源。

「准备阶段指令」把真实的 `/skill-name` 放在草稿开头，并附上所选阶段的目标和产物，保留已有文字后返回对话，由你检查并发送。同一个 Skill 的不同阶段会更新自动生成的阶段说明。含附件、引用或正在发送的草稿会暂时禁止插入。若项目或其他包覆盖了同名 Skill，页面会说明来源冲突，并禁止从该内置条目调用。

「会话执行」实时显示已记录的当前任务、下一步、待办、工具操作和文件记录。待办是否可用取决于会话的工具配置；默认 Super Code 模式可读取任务工具留下的记录。点击工具操作可查看详情；文件可在代码工作台打开，也可以关联到当前阶段。文件记录来自会话工具，不能代替 Git 差异或文件内容验收。工作台需要在设置中启用。

阶段有「待推进」「正在做」「受阻」「已验收」四种状态。同一流程只设一个当前阶段；受阻时填写原因，恢复后可以继续。填写成果说明或关联文件后，才能「确认阶段验收」。会话待办完成、工具成功或 AI 停止回复都不会自动通过阶段验收。已验收的阶段可以重新打开，原有成果仍保留。

每个会话的各条流程分别保存目标、阶段状态和成果。切换阶段时保留尚未保存的输入；保存某一阶段或目标不会顺带保存、丢弃其他输入。保存成功的记录刷新后仍可读取；失败时保留输入并提示重试。收藏、最近使用与阶段记录仅保存在当前浏览器，最多保留最近 32 个会话，不跨设备同步。旧版完成记录只迁移到含义相同的步骤，并标注尚无产物记录。

这里的流程卡表示作者方法的阶段衔接，不是工单依赖图。它不会自动调度任务、验证产物内容或同步 GitHub/GitLab 工单。

代码工作台的「所有操作」集中提供保存、查找、Git、设置等现有操作和已打开的文件。按 `Ctrl+Shift+P`（macOS 为 `Cmd+Shift+P`）打开，输入关键词，用上下方向键选择，按 Enter 执行，按 Escape 关闭。文件旁会显示未保存状态，不能执行的操作保持禁用。

## 自动维护内置资源

维护命令在源码仓库运行，需要 Node.js 22 或更新版本、npm、Git 和已登录的 GitHub CLI。先安装开发依赖。

```sh
npm run updates:check
npm run updates:apply -- --branch chore/bundled-updates
# 只处理指定包或依赖
npm run updates:apply -- --branch chore/oil-and-marked --only oil-ui,dependencies:marked
```

维护环境第一次安装依赖时可运行 `npm run updates:install`。它按锁文件使用项目原有的 DSH 测试版本，安装时暂时匹配开发用的 peer 声明，完成或失败后恢复公开的宿主兼容范围；不使用忽略 peer 冲突的安装选项。更新过程也会核对 DSH 依赖版本没有改变。

检查命令生成报告，不修改产品文件。应用命令要求当前工作区干净，在独立工作区创建指定本地分支；更新、构建、类型检查、测试和分发检查全部通过后，才创建本地提交。命令不推送、不合并，也不发布。再次从同一基线运行时，会复用干净的维护分支，对已更新的内容不再提交。

四个 Skill 包使用固定来源、固定提交和文件摘要。只下载需要分发且本地内容不同的文件；不执行上游安装器。oil-ui 保留插件内置版本的适配，不恢复其独立更新脚本。npm 默认只选择兼容版本，并检查新增或变化的直接及间接依赖许可证、来源、完整性和安装脚本；宿主兼容版本不参与通用升级。

需要适配的目标会列入报告，其他可更新的 Skill 或依赖继续处理。PStack 的 DSH 转换器锁定已审查版本；其升级需要同步检查宿主覆盖文件。OpenSpec 的 Skill 与 CLI 必须匹配，跨主版本需要单独适配。构建或测试失败时不创建提交，保留候选工作区和日志供排查；不会自动覆盖其中的修改。如果进程被强制结束，先检查候选与报告，再处理报错所指的残留锁。

报告默认位于 `.development/updates/run-*/report.json`，也可以通过 `--report` 指定位置。报告含本地工作区位置，不应直接作为公开文档上传。

仓库附带每周一次的 GitHub Actions 检查配置。将代码合入默认分支后才会进入定时调度；默认只检查。仓库变量 `SUPER_CODE_AUTO_UPDATE=true` 会启用自动更新，或在手动触发时勾选 `apply`。启用后，通过验证的结果推送到 `chore/bundled-updates-<运行编号>`，不会自动合并或发布；报告保留为该次运行的 artifact。
