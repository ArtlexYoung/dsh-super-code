# BusyBox Windows 长路径修复验收

2026-11-16，本地修复的 BusyBox 已接入 dsh-super-code 候选包。Windows 文件命令可处理本轮覆盖的长绝对路径、相对路径和中文文件名；实际 DSH 中，真实云模型通过随包 Bash 读取并修改了520字符路径的文件，冷重启后再次读取成功，桌面界面正常显示回答。文件内容由独立 Node 进程核对。

候选版本仍为 `0.4.1`，与已经发布的正式 `0.4.1` 不同，本轮没有发布。冻结 tgz 为17826550字节，SHA-256：

```text
9fae6cefd4d5c145b87f8b1bd115d8341ded364a35f7e3954c7f3fef0deaf839
```

## 对象与环境

产品从 `276d78fbfbe801de3d1b8829b22fac589155b589` 开始接入。BusyBox 从 `FRP-6354-g5f09fb446`（`5f09fb446adf81d005f0aad9dc47eca19ac3b74c`）修复，本地源码提交为 `ae1e80f2d53fc74381f49cf20ff0ae6371739afc`，产物版本为 `FRP-6354-sc-longpaths1`。

Windows 为隔离的 Windows 11 Enterprise ARM64 虚拟机。ARM64 程序原生执行，x64 程序由 Windows 兼容执行，没有 x64 实机结果。完整桌面程序使用官方 x64 DSH `0.2.2-rc.2`。构建使用 Linux amd64 隔离容器、固定 LLVM-MinGW `20261104` MSVCRT 工具链和 Unicode 两架构配置，不修改注册表或本机工具链。

仅 BusyBox 二进制、对应源码和说明发生变化，Bash、MSYS、GNU grep 及共同 npm 依赖文件字节保持不变。npm 包相对上一候选多出的两个依赖文件均为 CHANGELOG，没有升级运行依赖。

## 已知边界

本次修复在 Windows 文件接口边界转换宽字符路径，必要时使用扩展绝对路径。它不解决长进程工作目录、BusyBox Shell 的 `cd`、Bash、PTC或其他外部程序的限制；插件原有长工作目录使用原生工具的策略保留。

本虚拟机的UNC测试中，500字符源路径可重命名，511字符及以上的相应用例被BusyBox、Node和直接Windows API共同拒绝，失败时原文件内容保持完整。这是本环境的实测边界，不能推广为所有共享服务的统一长度限制。按句柄重命名的两个隔离原型也失败，没有加入产品代码。

八项基线已有失败为 `find // -maxdepth 0 -name /`、`realpath on non-existent absolute path 3`、三个sed用例（NUL命令、嵌入NUL、不存在标签），以及tar的hardlinks mode、symlinks mode、写入只读目录。没有通过削弱或删除这些测试消除失败。

离线安装结论仅针对显式 `--offline`。普通npm安装即使依赖随包提供，仍可能请求可选peer元数据并等待网络重试；本轮没有证明默认联网模式在禁网时快速完成。DSH和SSHFS-Win的目录、权限及原子写入问题没有纳入BusyBox修复。

## 验证过程中的纠正

初版UCRT构建不符合现有DLL闭包要求，最终改用MSVCRT，没有放宽检查。一次修改正在执行的构建脚本导致退出127，冻结脚本后重新完整构建与复现构建均成功。

早期测试因可执行文件名不为 `busybox.exe` 被解释为命令名；另有Windows临时目录8.3别名导致路径长度与realpath期望错误。最终先用Node原生realpath展开目录，再比较相同数据。回归脚本还强制新增长路径用例必须基线失败、候选通过，避免两边同时失败却被“无新增失败”误判。

首次桌面夹具未检查HTTP下载状态，空tgz被tar接受，该轮启动没有候选插件，结果无效。第二轮使用全新profile，强制HTTP成功、冻结包哈希匹配和入口文件存在，后续模型与冷重启验收均来自第二轮。冷重启后界面最初仍在加载，等待状态稳定后已显示同一会话两轮回答。

当前结论是本轮BusyBox文件命令修复和产品接入在上述环境通过专项验收；UNC系统限制、上游既有失败、x64实机和远程CI缺口继续明确保留。产品尚未发布，公开fork及上游PR也未创建。
