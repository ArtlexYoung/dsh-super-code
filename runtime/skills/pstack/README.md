# Maintaining the PStack DSH edition

The original, audited PStack distribution remains under `builtin/skills/pstack/`. Its `distribution.json` maps upstream paths to local files and SHA-256 hashes. Do not edit those files to adapt a workflow.

`convert.mjs` verifies the pinned revision and every original hash, then generates `pstack/dsh/`. The native provider loads only `dsh/skills/`. `adapt.mjs` translates host operations while retaining the workflow; `overrides/` replaces procedures whose host contract differs substantially, such as setup, history and bot UI. DSH.md and authoring.md are shared, on-demand references. No runtime prompt rewrite or agent execution layer is installed.

Run `npm run skills:build` after changing the adapter. `npm run skills:check` checks every generated byte, executable helper permissions, extra files, workflow links and known untranslated host dependencies. Both are part of normal build/test commands. The generated adaptation.json records the minimum DSH version and source/generated hashes for each file.

For an upstream upgrade, review the new revision and scripts first, update original files and provenance, then explicitly update the converter's revision gate. Revisit each host-specific procedure rather than only satisfying the text scan. Verify all native entrypoints, invocation flags, relative resources, actual tool schemas and representative live workflows on DSH 0.2.1-alpha.1 and later. Missing external capabilities must be reported precisely. Preserve host approvals and never treat a static check as proof of a live workflow.

When reviewing completeness, compare phases, role mappings, branches, outputs and finish predicates with the pinned upstream procedure. Entry counts and forbidden-word scans alone do not prove workflow preservation. Keep reasoning budget, panel size and concurrency distinct. Check host-specific rewrites separately from translations that retain the original phase sequence.
